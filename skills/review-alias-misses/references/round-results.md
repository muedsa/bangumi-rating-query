# 轮次结果记录规范

运行 `review-alias-misses` 时必须保留可排查的本地记录。仅审查或修改技能文件时不生成虚构运行记录。记录写入不代表对服务端操作的授权,批量方案仍须先复述并取得明确同意。

## 批次、轮次与文件

- **审核批次**对应 `SKILL.md` 中的“本轮”:从拉取待处理列表开始,同一列表的编号持续有效。用户明确开始新批次并重新拉取列表时才更换批次。
- **记录轮次**对应一次候选报告、方案复述待确认、执行结果汇总或暂停。首次报告为 `round-0001`,收到用户新回复后产生下一记录轮次;同一回复引发的中间进度快照不单独编号。确认方案的回复会产生新的记录轮次,继续引用原 `planId`。
- 默认根目录为启动任务时工作目录下的 `data/review-alias-misses/`,也可使用用户明确指定的结果目录。首次运行解析为绝对路径并告知用户;独立安装时不能把结果写进技能安装目录。本仓库的 `data/` 已被 Git 忽略,不要自动提交、上传或清理记录。
- `batchId` 使用 UTC 时间戳加随机后缀,例如 `20261027T083015123Z-a7c91e42`;不含 Windows 不支持的冒号,不能用原始别名作为路径。开始批次时创建独立目录,已有同名目录则换随机后缀,不得覆盖。
- 同一批次每个记录轮次留存一对 UTF-8 文件:

```text
data/review-alias-misses/20261027T083015123Z-a7c91e42/
  round-0001.json
  round-0001.md
  round-0002.json
  round-0002.md
```

JSON 用于追踪动作和结果,Markdown 用于直接阅读。已结束的记录轮次不可覆盖;后续确认、重搜、换绑、纠正或失败恢复另开记录轮次,用相同批次 ID、固定条目序号和相关方案 ID 关联。新批次中不得沿用旧序号执行动作。

## 保存时机与失败处理

1. 完成服务地址/参数检查后、首个 HTTP 请求前建立当前 JSON 记录,即使前置检查失败也能留下错误。新记录先写 `phase=running`,列表还未获取时用 `listFetched=false`,不要把“尚未读取”记成“空批次”。凭证缺失时也可先保存不含凭证的待配置状态。
2. 搜索完成一项就更新其关键词、候选摘要和状态。批量方案在等待用户确认时保存规范化动作清单、`planId` 和 `status=awaiting_confirmation`;不得把用户最初发送清单的时间记为确认时间。
3. 每个 HTTP 请求发出前保存其目标、目的、所属条目/动作与 `status=pending`;返回后保存实际状态、必要结果、错误及重试信息。发送前落盘失败则不要发送请求。请求结果未知的记录保留 `unknown` 或 `pending`,不能根据请求已经发出推断已成功。
4. 每个终态动作、冲突裁决、计划变更和验证结果后更新当前 JSON。可按条目合并数据,但保留本记录轮次内实际发生的请求顺序和用户确认依据;不要把后续重试成功覆盖成“从未失败”。
5. 每次准备结束回复或等待用户时,包括首次报告、待确认、重搜/冲突暂停、`stop`、错误中断、空批次和零处理,完成当前 JSON 与 Markdown,保存推荐命令,核对两个文件都存在且 JSON 可解析,再在回复中附两个文件的绝对路径链接。JSON 的 `endedAt` 代表记录轮次结束,不表示整个审核批次处理完。
6. 当前轮次文件更新时先写同目录临时文件,写入完成后替换当前文件;只更新本次正在进行的轮次,不替换历史轮次。临时请求正文的清理规则不适用于结果目录。
7. 文件保存失败或环境不能持久化文件时,明确报告“结果未完整保存”及已完成的服务端动作,保留已有文件并停止后续服务端写入,请求用户提供可保存位置。可在回复中提供脱敏结果供手动保存,但不能称为已落盘。突然中断可能只留下未结束的 JSON;恢复时先核对未知请求对应的服务端状态,不能直接重放。

本地记录用于排查和人工恢复,不是自动续跑检查点。读取旧记录不会授权其中的推荐命令、待确认方案或未完成动作;需要继续时重新核对当前服务端状态,按技能的方案确认规则执行。

## JSON 必备内容

使用标准 JSON 序列化,原始名称完整保存并转义控制字符。未知值用 `null` 或明确状态,不能编造响应、候选、时间或确认。

| 字段                                | 内容                                                                                                                                                                                                  |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schemaVersion`                     | 固定为 `1`,便于以后升级记录格式                                                                                                                                                                       |
| `batchId`, `round`                  | 批次 ID 与正整数记录轮次,与文件名一致                                                                                                                                                                 |
| `previousRound`                     | 上一记录轮次编号,首轮为 `null`                                                                                                                                                                        |
| `startedAt`, `updatedAt`, `endedAt` | UTC ISO 8601 时间;未结束时 `endedAt=null`                                                                                                                                                             |
| `phase`, `reason`                   | `running`、`awaiting_configuration`、`awaiting_confirmation`、`awaiting_choice`、`completed`、`stopped`、`failed` 或 `empty`,并说明原因;`completed` 只表示该方案完成,批次是否还有未处理项看 `summary` |
| `apiUrl`, `parameters`              | 不含凭证的目标根地址,实际 `limit`、`searchLimit`、`requestRetries`;地址尚不可用时为 `null`                                                                                                            |
| `listFetched`, `statistics`         | 是否已成功取列表,服务返回的访问/未命中统计开关;未获取的值为 `null`                                                                                                                                    |
| `summary`                           | 本批次截至当前的总数、绑定成功、冲突、跳过、无计划、失败、待裁决、未处理数量,各项不重复;额外单列重搜次数。列表未成功获取时数量为 `null`,空列表才为 `0`                                                |
| `items`                             | 当前整个批次的逐项快照:固定序号、原始 `name`、`normalizedName`、初始 `missCount` 与 `planned`、当前状态及原因;尚未搜索/执行的项也要包含                                                               |
| `plan`                              | 当前方案的 ID、按顺序展开的动作、复述时间、确认状态、确认时间和用户确认内容的必要摘录;没有方案时为 `null`。建议、待确认和已确认必须区分;变更后新 ID 关联 `supersedesPlanId`,原确认不能套用            |
| `events`                            | 本记录轮次按实际顺序发生的搜索、请求、用户决定、执行、冲突裁决与验证事件;每项有时间、条目序号/动作编号及结果,不复制其他轮次的事件冒充再次执行                                                         |
| `remainingActions`                  | 暂停时尚未执行的方案动作及是否已获确认;遇 `stop`/取消则记为取消,不能在下次自动续跑                                                                                                                    |
| `recommendations`                   | 本次总结给出的推荐回复/命令及理由,与实际执行事件分开;待批量确认时填当前 `确认执行 plan-...`,不是直接执行清单                                                                                          |

`items` 和 `events` 中至少保留以下排查信息,未发生的步骤明确标为未执行:

- 搜索:实际关键词、原文/简体/外站来源、每次 `total`、取回与展示数量,候选的真实 ID、完整原名/中文名、日期、形式、评分/人数、匹配层级、判断理由及来源链接。简介可按技能规则截断;重搜替换当前候选时,原结果仍留在旧轮次或当前事件中。
- 决策:用户选择的动作与条目 ID、确认的 `planId`、批量确认或 `bind!`/冲突单项确认的时间和范围。确认仅保存与该方案有关的必要摘录,不要复制整段会话或凭证。
- 写入:同步是否完成、`imported`、返回的 `alias.id/source/name/subjectId`、添加前别名快照、新增/复用/归属不确定的判断依据、`conflictingSubjectIds`、删除/换绑与计划变更的实际结果。
- 请求:HTTP 方法、相对路径、所属动作、必要的业务请求字段、HTTP 状态、`X-Request-ID`、每次尝试及退避时长、脱敏后的 `error.code/message`。未获得响应时状态码和请求 ID 为 `null`,记录超时/网络原因。
- 验证:验证是否执行、每项返回的 `status`、实际 `subject.id` 或候选 ID、`matchReason`、`matchedAliases` 和与目标是否一致。同步完成但别名添加失败、添加完成但验证失败必须分别记录。

只保存上述业务字段,不转储完整请求/响应对象、环境变量、Authorization/Cookie 或 Token。错误文本、用户回复及来源链接也须检查并去除凭证;不要假定错误体不会包含敏感信息。JSON 保留名称的真实文本,Markdown 使用技能中的安全展示规则。

## Markdown 与对话总结

Markdown 应独立可读,包含批次/轮次、起止时间、服务地址与参数、汇总计数、逐项处理结果、用户方案与确认状态、失败/冲突/未知结果、待处理项及推荐操作命令。完整名称、条目 ID、别名 ID 和请求 ID 应能定位到 JSON 中对应项。对话中可精简事件细节,但必须给出保存状态、两个文件链接和推荐命令。

推荐命令遵循 `SKILL.md` 第 8.1 步:填入实际序号和 ID,注明“复制回复给助手,尚未执行”。每条推荐须对应当前状态;既不能把建议当成已执行,也不能把“确认方案”误写成“绑定完成”。

新批次提示词可写成以下形式,实际输出替换为本次配置,不得保留示例地址或占位符,也不拼入 Token:

```text
请按 review-alias-misses 技能开始新一批审核,重新拉取待处理别名。
--api-url https://your-api.example.com --limit 10 --search-limit 10 --request-retries 5
先给候选报告和推荐操作命令,批量方案复述并得到我明确同意后再执行。
```

该提示词只供用户选择后发送,不能为了让报告里有下一批结果而提前执行。空批次注明“当前没有待处理记录,可稍后使用以上提示词再查”。
